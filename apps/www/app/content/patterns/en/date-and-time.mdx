How you ask users for date and time should be based on the information you actually need. Some dates are easy to remember, such as a date of birth, while others must be read from documents or cards. In some situations, an approximate date is sufficient, or a time relative to today. In other cases, users need to choose a date or time from a predefined set of options.

Avoid making the task more complicated than necessary. A standard text field, separate fields for day, month and year, the browser's built-in date picker or ready-made options can all be good solutions in different situations. Choose a solution based on the user's task and the functionality and control it requires.

## Known dates

When asking for known dates, such as a date of birth or wedding date, users should be able to type the date directly without having to navigate a calendar.

You can use one field for the whole date or separate fields for day, month and year. Separate fields can make it clear which parts of the date users need to provide, but they also add more focus stops, make it harder to paste a full date, and require users to understand how the date is split up. If you use separate fields, group them with `fieldset` and `legend` so that the relationship between them is clear.

When asking users to enter a date as it appears on a bank card, passport or other document, the order and format should match the document. This makes it easier to transfer the date accurately and reduces the risk of errors.

Make it clear which date format you expect. For example, you can state the date format in the label or description, so that the information is also available to screen reader users.

In the example above, we use `inputmode="numeric"` to provide a numeric keyboard on mobile phones and tablets. We deliberately avoid using `type="number"` for day, month and year. `type="number"` is designed for numeric values that can be incremented and decremented. It introduces functionality such as spin buttons and automatic validation. This is not always appropriate when users enter a date, and it can cause [accessibility issues (mozilla.org)](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/number#accessibility).

Allow flexibility in what users can enter. For example, accept both “5” and “05” for day and month, and both “90” and “1990” for year when it is clear which year the user means. If you require a specific format, make this clear, and error messages should explain exactly what is wrong.

## Date from a predefined set of options

If you know that users need to choose a date or time from a limited set of options, for example available appointments in the coming week, it may be more efficient to present these as ready-made choices.

When the number of options is very limited, such as a few dates or times, [`Radio`](/en/components/docs/radio/overview) can be a good choice. It allows users to quickly select an option without having to type anything.

### Let users narrow down the options

When the number of options increases, a [`Select`](/en/components/docs/select/overview) can be useful to narrow down the list. Users can choose preferred weeks, days or times, and then see the available options for that choice. Note: The example below does not work, because it is not connected to an actual set of dates. You should only show options that have available appointments. Avoid, for example, disabling weeks without availability, as this may create confusion. Explain in advance that only weeks with available times are shown, so users understand why some weeks cannot be selected.

## Specific date in the near future or past

When users need to choose a specific date close to today, visual support in the form of a calendar can be helpful.

An [`Input`](/en/components/docs/input/overview) with `type="date"` is one option. It allows users to enter the date directly or use the browser's built-in date picker. This way, you can use functionality that already exists in the browser, without developing and maintaining your own calendar control.

<Story story="NearFuturePastEN" />

Be aware that `type="date"` is controlled by the user's operating system and regional settings, not by the language of the website. This can result in the date being displayed in a format the user does not expect. Consider whether additional clarity is needed, for example by displaying the selected date in plain text with the month written out in words, or by otherwise confirming the date before it is saved.

Also be aware that functionality, appearance and interaction vary between browsers, operating systems and devices. You also have limited control over presentation, input and validation. Consider whether the built-in date picker meets your needs. If you need, for example, more precise control over which dates can be selected and how input works, a custom-built date picker may be a better choice. Whichever solution you choose, users should, as far as possible, be able to type the date directly when they know it.

## Start and end date

When users need to provide a period, the start date and end date should be clearly shown together. Use two separate fields and make it clear which date is which.

Place the fields in a logical order. If the dates depend on each other, validation must work both ways. If the user changes the start date, the end date may become invalid, and if the user changes the end date, the start date may become invalid. Error messages should explain what is wrong and how users can correct it.

<Story story="StartEndDateEN" />

Some users find it more efficient to choose the start and end date in a single calendar control. Since this does not exist as a built-in HTML control, the solution must be developed specifically for the purpose. Be aware that such a solution can be harder for some users to understand.

## Start and end time

When users need to provide a time interval, such as opening hours or the duration of a meeting, you can use an [`Input`](/en/components/docs/input/overview) with `type="time"`. It allows users to enter the time directly, while the browser provides support for choosing a time.

Use separate fields for start and end time, and display them clearly together.

## Approximate date

If users only need to provide month and year, they should be able to do exactly that. This is particularly relevant when the event took place a long time ago and users may not know the exact date.

## Date relative to another date

In some situations, it is more natural to ask for dates relative to another date, for example when users set up a reminder. In these cases, it may be better to use a [`Select`](/en/components/docs/select/overview) to offer options such as “1 hour before”, “1 day before” or “1 week before”. If the day of the week is important for the task, it should also be clearly displayed.

## Summary

Start with the need, and choose the solution that allows users to complete the task as quickly as possible. No single solution works best in every situation.

- Show ready-made options when the alternatives are limited
- Let users type the date directly when they already know it
- Only ask for as precise a date and time as the situation requires
- Consider whether the browser's built-in support (`type="date"` and `type="time"`) meets your needs, or whether you need a custom-built date picker with more functionality
